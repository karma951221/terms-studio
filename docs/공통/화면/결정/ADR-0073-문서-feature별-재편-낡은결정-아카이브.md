# ADR-0073 — 문서를 feature 별로 재편하고, 낡은 결정은 아카이브로 뺀다

> 상태: **채택** (2026-09-27 사용자 결정) · 날짜: 2026-09-27
> 개정 반영: 2026-09-27 2차 축소 (결정 3 — 현행 ADR 만 · feature 문서로 흡수 가능한 결정은 흡수) — 원본은 _archive/2026-09-27_문서재편/06_결정/
>
> 유저액션 파일 위치: [[공통/화면/유저액션_작성원칙]] (기능 문서 §4). 진입점: [[README]].

## 맥락

문서가 작업 단위(01_기획 · 02_UI · 03_설계 · 04_실행 · 05_QA · 06_결정 · superpowers) 폴더로 나뉘어 있었다.
그래서 기능 하나를 이해하려면 기획 · 화면기획 · 유저액션 · 시나리오 · spec · ADR 을 폴더 여섯 곳에서 모아 읽어야 했다.
ADR 72건 중 35건이 뒤에서 번복 · 개정됐는데도 같은 폴더에 나란히 있어서, 낡은 결정이 현재 규칙처럼 읽혔다.
README 의 「지금 상태」 절도 날짜별 변경 로그로 불어나, 현재 규칙을 한눈에 읽을 수 없었다.

2026-09-22 에 feature 9개와 「ADR 은 전부 남기고 배너로 번복 표시」 안으로 한 번 합의했다. 하지만 실행하지는 않았다.

## 결정

1. **feature = 앱 메뉴 항목 = route · `src/domain` 폴더.** 10개다: 마스터 · 구분자 · 담보 · 담보속성 · 공용조항 · 문면 · 별표 · 상품 · 조립산출 · 관계정보. (재편 때 11개 — 「유형」은 2026-09-27 마스터의 둘째 탭으로 흡수됐다, [[기능/마스터/마스터]] §6.2.)
   feature 밖은 `공통/화면` · `공통/기술` · `QA` · `실행` · `00_시작` 에 둔다.
2. **feature 문서는 하나로 합쳐 새로 쓴다.** `기능/<f>/<f>.md` 한 문서에 한 줄 · 코드 위치 · 규칙 · 화면(유저액션 포함) · 미결 · 결정 · 시나리오를 담는다(`_템플릿/기능.md`).
   feature 폴더 안에 따로 두는 것은 `시나리오/` 와 `결정/` 둘뿐이다. 시나리오는 파일명을 그대로 유지한다 — E2E 가 파일명을 좌표로 쓴다.
3. **ADR 은 현행만 · feature 문서로 흡수 가능한 결정은 흡수한다(§6 결정 메모).**
   - **ADR 로 남기는 기준은 둘 다 만족할 때만이다** — ① 여러 기능에 걸치거나 아키텍처 · 데이터 모델의 뼈대를 정한다(한 기능 문서 안에 두면 다른 기능 쪽에서 근거를 못 찾는다) ② 버린 대안이 다시 제안될 만하고, 규칙만 봐서는 왜 그런지 알 수 없다. 애매하면 흡수한다.
   - **흡수**: 현행 규칙은 feature 문서 §3 · §4 에(이유가 안 보이면 규칙 아래 `— 왜: …` 한 줄), 결정 · 이유 · 버린 안은 §6.2 결정 메모 한 행으로. 공통(`공통/화면` · `공통/기술` · `QA`)은 각 대표 문서의 「결정 메모」 절로. 흡수된 ADR 파일은 `docs/_archive/2026-09-27_문서재편/ADR흡수/` 로 옮기고 번호는 사라진다.
   - 남긴 ADR 은 feature 문서 §6.1 에 싣는다. 유효한 feature ADR 은 `기능/<f>/결정/` 에 둔다.
   - 일부 조항만 개정된 ADR 은 현행 내용으로 고쳐 쓰고, 원본을 아카이브에 사본으로 둔다.
   - 번복 · 보류 · 미채택 ADR 은 `docs/_archive/2026-09-27_문서재편/06_결정/` 으로 뺀다.
   - 남긴 ADR 의 번호와 파일명은 바꾸지 않는다 — 코드 주석이 번호로 가리킨다. 흡수된 번호를 가리키는 코드 주석은 흡수된 feature 문서 절(예: `기능/담보 §3.2`)로 일괄 치환한다.
4. **아카이브는 리포에 올리지 않는다** — `.gitignore` 에 `_archive/` 를 넣어 어느 깊이의 백업 폴더든 제외한다.
5. **위키링크는 docs 기준 전체 경로로 쓴다.** 링크 검사는 `npm run docs:links` 로 한다.
6. **git 을 다시 시작한다.** 재편을 마친 코드 + 문서 전체를 첫 커밋 하나로 삼는다.

## 이유

- feature 경계를 메뉴 · route · domain 폴더와 맞추면 코드 폴더와 문서가 1:1 로 이어진다. 그러면 기능 문서 §2 「코드 위치」 하나로 양방향 탐색이 된다.
- 읽는 사람에게 필요한 것은 결정의 경위가 아니라 현재 규칙이다. 경위는 ADR 이 맡는다.
- 1차 재편 뒤에도 ADR 이 62건이었고 대부분이 화면 배치 · 문구 · 기능 안 세부 규칙이었다. 규칙은 feature 문서 §3 에, 결정은 ADR 에 나뉘어 같은 내용을 두 번 읽어야 했다. 한 기능 안의 결정은 이유 한 줄 · 버린 안 한 줄이면 충분하다 — 긴 ADR 이 값을 하는 것은 여러 기능이 기대는 뼈대 결정뿐이다.
- 개정된 ADR 을 원본 그대로 두면 「어느 조항이 살아 있나」를 다시 추적해야 한다. 고쳐 쓰면 ADR 하나가 곧 현행 결정이 된다.

## 버린 대안

- **2026-09-22 안(feature 9개 · ADR 전부 유지 + 배너)**: 동적표 · 실물재현을 feature 로 두어 코드 폴더와 어긋났다. 번복 ADR 이 폴더에 남아 문제 (b) 도 풀리지 않았다.
- **종류별 파일 유지(`기획.md` · `화면.md` · `액션.md` 를 feature 폴더로 옮기기만)**: 안전하지만, 한 기능을 여러 파일에서 모아 읽는 문제가 그대로 남는다.
- **ADR 을 전부 아카이브하고 feature 문서에 녹이기**: 뼈대 결정(null 없음 · 코드/표시명 · 식 언어 · 역할 등)의 맥락 · 버린 대안 · 감수 비용이 리포에서 사라져 같은 대안이 다시 제안된다. 그래서 두 기준을 만족하는 것만 남긴다(결정 3).
- **ADR 을 전부 남기고 §6 에 목록만**(1차 재편): 기능 안 세부 결정까지 ADR 로 남아 규칙과 결정을 두 곳에서 읽어야 한다.

## 결과와 감수하는 비용

- **이력이 사라진다.** 번복 ADR · 옛 기획 · 개정 전 원본은 로컬 아카이브에만 남는다. 아카이브는 리포 밖이라 다른 기기나 새 클론에서는 볼 수 없다.
  이번 git 재시작으로 옛 커밋 이력도 없다.
- **feature 문서는 초안이다.** 에이전트가 원천 문서를 현행 ADR · 코드와 대조해 새로 썼다. 원천과 코드가 어긋난 곳은 코드를 현재로 적었고, 결정됐지만 코드에 없는 것은 **미구현**, 결정이 안 된 것은 §5 **미결**에 모았다.
  사용자 검토 뒤 상태를 「합의」로 올린다.
- **본문이 낡은 시나리오가 있다.** 옮긴 시나리오 중 일부(담보트리 · 담보값입력 · 담보속성탑재 · 폼입력 · 구분자정의 · 공용조항)는 폐지된 전제(모드 · 부착 · 구조체)를 담고 있다. 개정 대기다.
- **흡수된 결정의 긴 맥락은 로컬 아카이브에만 남는다.** feature 문서의 결정 메모는 한 행이라 짧다. 코드 주석의 흡수된 번호는 일괄 치환 전까지 아카이브를 가리킨다.
- **새 결정을 낼 때 먼저 기준을 본다.** 두 기준을 못 넘으면 ADR 을 쓰지 않고 feature 문서 §3 과 §6.2 결정 메모에 바로 적는다.
- **옛 결정을 뒤집는 새 ADR 을 낼 때 할 일이 생긴다.** 옛 ADR 을 아카이브로 옮기거나(번복) 현행으로 고쳐 쓰고(개정), 해당 기능 문서 §6 결정 표도 같은 커밋에서 고쳐야 한다.
