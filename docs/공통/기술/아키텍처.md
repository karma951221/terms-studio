> 상태: 초안 · 최종수정: 2026-10-07

## 경계와 책임

- **규칙은 도메인에, 저장은 repo 에, 조합은 서비스에.** 서비스는 `(actor, …) → Result<T>` 를 돌려주고,
  거부는 `Rejection` 6종(forbidden · duplicate · minimumStructure · needsConfirmation · invalid · notFound)으로만 표현한다.
  화면은 거부를 표시할 뿐 판단하지 않는다 — 「숨김 ≠ 잠금」.
- **파괴적 액션은 한 프로토콜**(`destructive()`): assertCan(editor 거부) → precheck(최소 구조·notFound) →
  confirm 없으면 `needsConfirmation(Impact)` → confirm 이면 실행. 모든 영역이 같은 함수를 쓴다.
- **영역 간 결합은 주입 인터페이스로 끊는다.** 각 영역 서비스는 다른 영역을 import 하지 않고
  인터페이스(ImpactSource · UsageSource · ClauseGate · TypeResolver · CoverageMasterSource ·
  GeneralAttachmentCheck · OptionValidator · AttributeRefSource · Attacher)를 받는다.
  `container.ts` 가 유일하게 전부를 알고 연결한다. 순환 의존은 지연 참조.
- **참조는 그래프다.** refs 가 카탈로그·공용조항·문서·부착·조합·오버라이드에서 간선을 만들고,
  사용처 역조회·영향(Impact.brokenRefs)·관계정보·무결성을 낸다. 참조 추가 시점 검증은 각 영역이,
  삭제 영향·조립 시점 오류는 refs·assembly 가.
- **문맥은 언어 밖이다.** 식 언어는 `EvalContext`(lookup · attribute · children)를 주입받는다.
  담보 마스터 문맥(coverage.evalContext)·상품담보 스냅샷 문맥(assembly.context)이 각각 만든다.

### 다중산출 제약 (2026-09-09 · [[기능/조립산출/결정/ADR-0034-다중산출-1급-조립결정성]])

전 상품 204건 전량 산출이 **주 산출 경로**이고 1건 미리보기가 특수한 경우다.
파이프라인을 고칠 때 다음을 어기지 않는다:

- **재료는 「공유 마스터 / 상품 고유」로 쪼갠다.** `AssemblyInput` → `MasterBundle` + `ProductInput`,
  조립 서명은 `assemble(master, product)`. 마스터는 실행당 1회 적재.
  지금 `services/assembly.ts` 의 `load()` 는 `clause.list()` · `document.listAppendices()` ·
  `catalog.list()` · `catalog.listEnums()` · `product.listAttributeKinds()` 를 **상품마다** 다시 읽는다.
- **상품당 적재 쿼리 수는 상수.** 담보·세목·급부 수에 비례하는 쿼리 루프 금지 — repo 에 일괄 조회 계열을 둔다.
  (지금은 owner 하나당 `listAttached` 한 방씩 직렬로 돈다.)
- **파이프라인은 결정적이다.** 전역 상태 · 모듈 캐시 · 누적 카운터 · `Date.now()` · 난수 금지.
  같은 입력이면 어느 워커에서 언제 돌려도 같은 `Booklet`. **순수층 ESLint 가 이걸 다 막지는 못한다 — 리뷰 항목이다.**
- **산출은 요청 밖의 장기 실행 프로세스에서 돈다.** Vercel 서버리스에서는 2~3시간 잡을 돌릴 수 없다([[공통/기술/기술스택]]).
- **다중이 원형인 서명으로 짓는다** — 1건 함수를 먼저 만들고 나중에 감싸지 않는다.

## 트랜잭션 규칙 (PGlite)

PGlite 는 단일 연결이다. **트랜잭션 안에서 바깥 `db` 핸들로 쿼리하면 영구 대기**한다(2차 구현에서 두 번 실증).
서비스는 `db.transaction(tx => …)` 안에서 repo 에 반드시 `tx` 를 넘기고, 주입 소스는 조립 루트가 `contextualDb()` 프록시로
감싸 열린 tx 를 자동으로 타게 한다. 서버 Postgres 로 넘어가도 이 규칙은 해롭지 않다.

## 요구사항 (범위 문서에서)

- **다른 문서 종류(별지)가 같은 데이터에서 나와야 한다** — 문서 노드 종류는 규칙 테이블로 열려 있고,
  파이프라인 단계는 각각 순수 함수라 별지 파이프라인은 단계를 다시 조합하면 된다.
- **다중산출을 1급으로 둔다** (2026-09-09) — 조립·적재·저장이 「상품 1건」을 전제로 굳으면 안 된다.
  전량 204건이 원형이다 → 위 「다중산출 제약」 · [[기능/조립산출/조립산출]].
- **기본계약·보통약관을 단수로 하드코딩하지 않는다** (2026-09-04) — `product_base_contracts` 는 복수 허용,
  「정확히 1개」는 검증 규칙이다. 특약 그룹은 담보의 열거값이라(ADR-0080) 그룹 ↔ 보통약관 템플릿 자리는 없다 — 다중 보통약관 때 다시 정한다.

## 시드와 초기 데이터 (2026-09-06 확정)

- **시작 상태 = 관통 1 축약 픽스처(최소 시드).** 알파Plus 이관은 그 위에 덧붙인다. 빈 마스터로 시작하는
  안은 이관 초기에 화면 검증 대상이 없고, 실물 시드는 이관이 끝나야 생긴다.
- **시드의 정본은 데이터 파일이다** — `src/db/seed/data/*.json` (영역별 파일: 구분자·담보속성·담보·공용조항·
  문면·보통약관·별표·상품). 시드 코드는 파일을 읽어 **서비스 계층을 통해** 넣는다 (repo 직접 쓰기 금지 —
  검증·채번이 그대로 돈다). 파일 안의 참조는 uuid 가 아니라 **코드**로 쓴다.
- JSON 을 쓴다 — YAML 은 파서 의존성이 늘고, 리포 규칙이 새 npm 의존성을 막는다.
- 이 파일 형식이 곧 **내보내기(export) 형식**의 씨앗이다 — 실물 이관이 끝나면 같은 형식으로 내보내
  실물 시드로 키운다 (2차기획 목록 「실행 준비」 후속). 스키마가 바뀌면 시드 파일도 같은 커밋에서 고친다.
- `src/db/seed/load.ts` 가 영역별 JSON을 의미 코드로 연결해 서비스 API로 적재한다. `alphaPlus.ts` 는 호환 진입점만 제공한다.
