## 확정 (2026-08-30 의뢰인)

| 영역 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | **Next.js** (App Router, TypeScript) | 선호 스택. 프론트+API 한 몸 — 혼자 개발에 유리 |
| 개발 DB | **PGlite** (임베디드 Postgres) | 로컬 파일로 도는 진짜 Postgres — 설치·마이그레이션 비용 최소화 |
| 배포 | 개발은 로컬 전용 → 배포 시 **Vercel** | — |

## 부속 결정 (2026-08-30 채택)

| 영역 | 선택 | 이유 | 상태 |
|---|---|---|---|
| ORM·마이그레이션 | **Drizzle** | PGlite 공식 드라이버 지원이 매끄럽다. 스키마가 TS 코드라 타입 공유 | ✅ 채택 |
| 검증 | **zod** | 폼 = 구조체 렌더러의 값 검증과 API 입력 검증을 한 정의로 | ✅ 채택 |
| 테스트 | **Vitest + Playwright 분담** — 조립·조건평가·파생·번호계산은 Vitest 문서트리 스냅샷(대부분), 에디터·폼 등 핵심 화면 흐름만 Playwright E2E(소수 정예) | 조립 검증을 E2E 로 하면 느리고 원인 추적이 섞인다 — 「조립이 틀렸다」와 「화면이 깨졌다」의 분리 | ✅ 채택 |
| 프로덕션 DB | Postgres 호환 (Neon 등) | PGlite 와 같은 엔진 — 마이그레이션 그대로 이관 | 나중에 결정 |

## 제약으로 기록해 둘 것

- **권한 분리가 온다** — 지금은 혼자 쓰지만 향후 여러 명 + 권한 구분.
  MVP 에서 인증·권한을 만들지 않되, **스키마와 API 가 사용자 개념을 원천 배제하지 않게** 한다
  (예: 변경 이력에 who 자리). 개발/프로덕션 모드의 서버 거부 골격이 권한 체계의 앞선 모습이기도 하다.
- PGlite 는 단일 프로세스 임베디드다 — 여러 명이 쓰는 시점에는 서버 Postgres 로 넘어간다.
  그 전환이 아프지 않도록 **PGlite 전용 기능에 기대지 않는다** (표준 Postgres SQL 만).
