# E2E 관측·복구 장치 설계

> 상태: 합의 · 최종수정: 2026-09-08
> 관련: [[QA/테스트전략]] · [[QA/시나리오_작성규칙]] · [[QA/시나리오/실물재현_E2E_시나리오]]

## 1. 왜 만드나

E2E 를 **사람은 시나리오 문서로 정의하고, 에이전트가 실행·진단·복구**하게 만든다.
지금은 셋 다 막혀 있다.

| 막힌 곳 | 현재 |
|---|---|
| 증거가 없다 | `reporter: "list"` — 파일로 남는 게 없다. `trace: "on-first-retry"` + 로컬 `retries: 0` 이라 **로컬에서 trace 가 한 번도 안 찍힌다**. console·pageerror·네트워크 미수집 |
| 서버가 안 보인다 | 조작이 전부 서버 액션 POST 인데, `webServer` 가 dev 서버 stdout/stderr 를 삼킨다 — **서버 액션 예외·Drizzle 에러가 통째로 소실**된다 |
| 재현이 안 된다 | `alpha-plus.spec.ts` 가 `Date.now()` 로 이름을 만들고 개발 DB 에 누적된다. `reuseExistingServer` 까지 켜져 있어 같은 상태로 되돌아갈 수 없다 |
| 심판이 없다 | 실패했을 때 「테스트를 고쳐 통과시키기」가 언제나 가능하다. 에이전트의 자율 복구가 곧 스펙 침식이 된다 |

마지막이 핵심이다. **시나리오 문서를 정본으로 세우면 심판이 생긴다.**
실패는 셋 중 하나로 갈리고, 각각 조치가 다르다.

| 판정 | 뜻 | 조치 |
|---|---|---|
| ① | 테스트가 문서를 잘못 옮겼다 | 테스트 수정 — 에이전트 자율 |
| ② | 코드가 문서를 어겼다 (진짜 회귀) | 코드 수정 — 에이전트 자율, 금지목록 제외 |
| ③ | 문서가 낡았다 (기획이 바뀌었다) | **에이전트 정지. 사람이 문서를 고친다** |

③이 없으면 자율 복구는 반드시 스펙을 갉아먹는다.

## 2. 사람이 쓰는 법

이 장이 이 장치의 실제 인터페이스다. 사람이 하는 일은 **시나리오 문서를 쓰는 것 하나**다.

### 2.1 테스트 내용은 시나리오 문서에 쓴다

`docs/기능/<f>/시나리오/<흐름>_시나리오.md` 에 지금 쓰던 형식 그대로 한 절을 추가한다.
새 형식을 배울 것은 없다 — 14개 문서가 이미 이 골격이고, [[QA/테스트전략]] 이
*「테스트 설명은 시나리오 문장 그대로 — 역방향 대조가 곧 테스트 목록」* 이라고 선언해 둔 그것이다.

```markdown
## 시나리오 5 — 별표 목록 순서를 바꾸면 본문 번호가 따라 바뀐다

**전제**: 알파Plus 상품에 별표 목록 21건이 등록돼 있고, 조립 미리보기가 오류 0 · 완성본이다.
본문 어딘가가 「장해분류표」를 별표 참조 슬롯으로 가리킨다.
**흐름**:
1. 상품 화면의 별표 목록 편집칸을 연다.
2. 「장해분류표」 코드를 목록 맨 앞으로 옮기고 저장한다.
3. 조립 미리보기를 연다.
**기대 결과**: 「장해분류표」의 별표 번호가 1이 되고, 본문의 별표 참조 렌더가 【별표1】로 바뀐다.
원래 1번이던 별표는 2로 밀린다 — 목록 순서가 곧 번호다.
**경계·오류**:
- 목록에 없는 코드를 본문이 참조하면 조립 오류 + 좌표 보고.
- 번호를 본문에 직접 타이핑하는 경로는 없어야 한다.
```

지켜야 할 것은 네 굵은 글씨 라벨(`전제` · `흐름` · `기대 결과` · `경계·오류`)과
`## 시나리오 N — 제목` 머리뿐이다. **내용은 산문으로 써도 된다** — 파서는 문단 경계만
읽고, 문장 자체는 실행하지 않고 인용만 한다.

이 절의 좌표는 자동으로 `그룹핑별표#5` 가 된다 (파일 슬러그 + 시나리오 번호).
흐름 2단계는 `그룹핑별표#5.2`. **문서에 ID 를 손으로 달 필요는 없다.**

### 2.2 에이전트에게 지시하는 법

지시는 네 가지면 충분하다.

**(1) 새로 쓴 시나리오를 테스트로 만들어라**

> 「그룹핑별표 시나리오 5 새로 썼어. E2E 만들어줘」

에이전트는 그 절을 읽고 `tests/e2e/` 에 좌표가 달린 test 를 쓴다.
흐름 단계 하나가 액션 하나로 대응한다.

**(2) 실행하고, 깨졌으면 고쳐라**

> `/e2e`                 — 전부 실행 → 실패하면 자율 복구 루프
> `/e2e 그룹핑별표`        — 그 문서의 시나리오만
> `/e2e 그룹핑별표#5`      — 그 시나리오 하나만

**(3) 무엇이 안 덮여 있나**

> 「E2E 커버리지 보여줘」  (= `npm run e2e:coverage`)

**(4) 기획이 바뀌었다**

문서를 먼저 고치고 (2)를 부른다. 문서가 정본이므로 순서가 반대면 안 된다.

> ⚠ **「테스트 통과시켜줘」라고 지시하지 말 것.** 그건 ①②③ 판정을 건너뛰고
> 초록불을 목표로 삼으라는 지시가 된다. 올바른 지시는 언제나
> **「문서대로 맞는지 확인해줘」**다. 통과는 결과이지 목표가 아니다.

### 2.3 결과가 어떻게 보이나

**통과했을 때** — 터미널에 좌표와 액션이 그대로 찍힌다. 시나리오 문서를 읽는 것과 같다.

```
  ✔ 그룹핑별표#5  별표 목록 순서를 바꾸면 본문 번호가 따라 바뀐다  (18.2s)
      ✔ #5.1  별표 목록 편집칸을 연다                 0.9s
      ✔ #5.2  장해분류표를 맨 앞으로 옮기고 저장한다     2.4s
      ✔ #5.3  조립 미리보기를 연다                    14.1s

  6 passed  ·  golden=a1b2c3d4  ·  38.6s
```

**커버리지** — 문서 ↔ 코드 역방향 대조표. [[QA/테스트전략]] 이 선언만 해두고
사람이 수동으로 지키던 그것을 기계가 낸다.

```
문서                시나리오   흐름단계   E2E        미커버
문면작성                 7        41     #1 #7       #2 #3 #4 #5 #6
그룹핑별표               5        22     #5          #1 #2 #3 #4
조립오류                 6        33     —           전부
…
합계                    83       312     78 (25%)
```

좌표가 없는 `test` 는 리포터가 실패로 처리한다 — 태그를 빠뜨리면 조용히 새지 않는다.

### 2.4 실패했을 때 무엇이 남나

실패 1건마다 디렉토리 하나가 생긴다. **`FAILURE.md` 한 장이 진단서이자 프로토콜**이다 —
에이전트는 이것만 읽고 시작하고, 사람도 이것만 읽으면 된다.

```
test-results/그룹핑별표#5/
  FAILURE.md          ← 이것부터 읽는다
  timeline.txt        ← 브라우저·서버·네트워크가 시각 순으로 한 줄씩
  before.png          ← 실패한 액션 직전
  at-failure.png      ← 실패 순간 (full page)
  trace.zip           ← npx playwright show-trace 로 열어 되감기
  server.log          ← dev 서버 원본 (타임스탬프 부착)
  pgdata/             ← E2E_DUMP_DB=1 일 때만
```

`FAILURE.md` 는 이렇게 생겼다.

```markdown
# 실패: 그룹핑별표#5 — 별표 목록 순서를 바꾸면 본문 번호가 따라 바뀐다

## 정본  (docs/기능/상품/시나리오/그룹핑별표_시나리오.md:41)
전제: 알파Plus 상품에 별표 목록 21건 … 조립 미리보기가 오류 0 · 완성본이다.
흐름: 1. 편집칸을 연다  2. 맨 앞으로 옮기고 저장한다  ← 여기서 실패  3. 미리보기를 연다
기대 결과: 「장해분류표」의 별표 번호가 1이 되고 … 목록 순서가 곧 번호다.

## 무슨 일이 있었나
  ✔ #5.1  별표 목록 편집칸을 연다                  0.9s
  ▶ #5.2  장해분류표를 맨 앞으로 옮기고 저장한다      ✗ 30s timeout
           대기: getByRole("heading", { name: /별표 목록 21건/ })

## 같은 구간의 증거
  [서버 12:04:31.2] Error: 별표 코드가 중복됩니다: APX02_DISABILITY
                       at saveAppendices (src/services/product.ts:212)
  [POST  12:04:31.4] /products/8f2a…  →  500  (240ms)
  [콘솔  12:04:31.6] An error occurred in the Server Components render.

## 재현
  golden=a1b2c3d4
  npm run test:e2e -- --grep "그룹핑별표#5"

## 판정 — 하나를 고르고 위 「정본」 문장을 인용할 것
  [ ] ① 테스트가 문서를 잘못 옮겼다   → 테스트 수정 (허용)
  [ ] ② 코드가 문서를 어겼다         → 코드 수정 (허용, 금지목록 제외)
  [ ] ③ 문서가 낡았다               → 수정 금지. 멈추고 사람에게 보고

  금지: src/domain/**/__snapshots__/**  ·  tests/fixtures/terms/*.md
        docs/**/시나리오/*.md
  근거 인용이 없으면 수정 금지. 금지목록을 건드려야 통과한다면 그건 ③이다.
```

**③으로 판정되면 에이전트는 아무것도 고치지 않고 멈춘다.** 사람이 받는 보고는
「문서는 X 라는데 코드는 Y 다. 어느 쪽이 지금 기획인가?」이고, 사람이 문서를 고치면
그때 (2)를 다시 부른다.

## 3. 설계

### 3.1 결정론 — golden 스냅샷

개발 DB 는 PGlite **파일 디렉토리**(`.data/pgdata`)이고 `PGLITE_DATA_DIR` 로 위치를
갈아끼울 수 있으며, 시드는 멱등이다. 즉 DB 상태 전체가 `cp -R` 로 복사된다.

PGlite 인스턴스는 dev 서버 프로세스의 `globalThis` 에 캐시되므로, DB 를 갈아끼우려면
서버를 새로 띄워야 하고 복사는 기동 **전에** 끝나야 한다. `globalSetup` 과 `webServer` 의
실행 순서에 기대는 대신 명령줄로 순서를 못박는다.

```ts
webServer: {
  command: `tsx scripts/e2e/prepare-db.ts && tsx scripts/e2e/dev-with-log.ts --port ${PORT}`,
  env: { PGLITE_DATA_DIR: ".data/e2e-run" },
  reuseExistingServer: false,
}
```

`scripts/e2e/prepare-db.ts`:

1. golden 키 = `drizzle/**` + `src/db/schema/**` + `src/db/seed/**` 내용 해시
2. `.data/e2e-golden-<키>/` 가 없으면 그 경로로 시드를 1회 실행
3. `rm -rf .data/e2e-run && cp -R .data/e2e-golden-<키> .data/e2e-run`

얻는 것: `alpha-plus.spec.ts` 의 `Date.now()` 를 없애고 고정 이름을 쓴다.
재현 좌표가 `golden 해시 + 시나리오 좌표` 두 줄로 줄어, 무거운 상태 덤프가 평시엔 불필요해진다.

**대가**: `reuseExistingServer: false` 라 실행마다 Next dev 부팅(5~15초)이 붙는다.
탈출구로 `E2E_FAST=1` — 스키마·시드 해시가 그대로이고 `.data/e2e-run` 이 깨끗하면 재사용한다.
CI 에서는 무시한다.

### 3.2 증거 수집 — 하나의 타임라인

`tests/e2e/_lib/fixtures.ts` 가 `test` 를 확장해 재수출한다. 테스트마다 시각 순 단일 배열에 모은다.

| 출처 | 방법 |
|---|---|
| 액션 경계 | `ev.action(좌표, 이름, fn)` → `test.step` + 타임라인 마커 |
| 브라우저 콘솔 | `page.on("console")` |
| 페이지 예외 | `page.on("pageerror")` |
| 서버 액션 POST | `page.on("response")` — 상태·URL·소요 |
| 요청 실패 | `page.on("requestfailed")` |
| **dev 서버 로그** | `dev-with-log.ts` 가 stdout/stderr 각 줄에 ISO 타임스탬프를 붙여 `server.log` 로 |
| 스크린샷 | 액션 경계마다 촬영, 실패 시에만 보존 + 실패 순간 full-page |

굵은 행이 가장 크게 비어 있던 조각이다. Next dev 로그에는 타임스탬프가 없으므로
얇은 래퍼로 감싸 붙이고, 리포터가 실패 구간의 시간 범위로 잘라 온다.

`trace` 는 `"retain-on-failure"` 로 바꾼다.

### 3.3 문서 좌표

**시나리오 문서는 건드리지 않는다.** `파일슬러그#시나리오번호` 가 이미 유일하다.

`scripts/e2e/scenarios.ts` 가 `docs/**/시나리오/*.md` 를 파싱해
`{좌표, 제목, 전제, 흐름[], 기대결과, 경계오류[]}` 로 만든다. 산문은 문자열로 보존해 인용에만 쓴다.
`실물재현_E2E_시나리오.md` 는 절차 문서라 이 체계에서 제외한다.

코드 쪽은 Playwright 정식 annotation 을 쓴다 — 리포터가 `test.annotations` 로 구조적으로 읽는다.

```ts
test("별표 목록 순서를 바꾸면 본문 번호가 따라 바뀐다",
  { annotation: { type: "시나리오", description: "그룹핑별표#5" } },
  async ({ page, ev }) => {
    await ev.action("그룹핑별표#5.1", "별표 목록 편집칸을 연다", async () => { … });
  });
```

`npm run e2e:coverage` 가 §2.3 의 표를 낸다.

### 3.4 진단서 리포터

커스텀 Playwright 리포터가 실패마다 §2.4 의 디렉토리를 만든다.
「정본」 절은 파서가 준 원문을 그대로 붙이고, 「같은 구간의 증거」는 실패한 액션의
시작~종료 타임스탬프로 타임라인을 잘라 넣는다.

진단서 안에 판정 기준과 금지 목록을 함께 박는 것이 의도다 — 에이전트가 별도 규칙 파일을
읽지 않아도 심판과 금지선이 눈앞에 있다.

### 3.5 복구 루프

정본은 `docs/QA/E2E_복구절차.md`. `.claude/commands/e2e.md` 는 그것을 가리키는 얇은 진입점.

1. `npm run test:e2e` → 녹색이면 종료
2. `FAILURE.md` 를 읽고 ①②③ 판정 — **정본 인용 필수**
3. ③ → 즉시 정지, 사람에게 보고
4. ①② → 수정. 금지 목록을 건드려야 하면 ③으로 강등하고 정지
5. `npm test && npm run typecheck && npm run lint` 녹색 확인
6. 1로 — **최대 3회.** 초과하면 ③ 취급하고 정지
7. 수정은 건별 커밋

안전핀 넷: 금지 목록 · 판정 근거 의무 · 3회 상한 · 건별 커밋.
②의 가장 위험한 형태인 「스냅샷·원문을 갱신해서 통과시키기」는 금지 목록이 봉쇄한다.

## 4. 만드는 순서

1. **결정론** — `prepare-db.ts` · `dev-with-log.ts` · `playwright.config.ts`.
   이게 없으면 나머지가 전부 무의미하다
2. **증거 fixture** + 서버 로그 결합
3. **`FAILURE.md` 리포터**
4. **문서 파서 + annotation + 커버리지**
5. **복구절차 문서 + 슬래시 커맨드**
6. **(선택) 실패 시 `pgdata` 덤프** — `E2E_DUMP_DB=1`, 최근 3건만 보존

기존 `alpha-plus.spec.ts` · `smoke.spec.ts` 는 fixture import 교체 · annotation 부착 ·
`Date.now()` 제거만 한다. `firstMismatch` 등 대조 로직은 손대지 않는다.

## 5. 버린 대안

| 갈림길 | 고른 것 | 버린 것과 이유 |
|---|---|---|
| 액션 정의 위치 | **기존 시나리오 문서 (C)** | 코드 안 래퍼(A) — 사람이 TS 를 만져야 한다. YAML DSL(B) — 새 형식을 배워야 하고 기존 문서 자산이 죽는다 |
| 문서↔코드 결합 | **앵커 (C2)** — spec 이 소스, 좌표를 태그로 | 생성 (C1) — `alpha-plus.spec.ts` 의 도메인 특유 대조 장치가 생성물로 환원되지 않고, 재생성이 수작업을 덮어쓴다. 런타임 파싱 — 흐름이 산문이라 불가능 |
| 재현 방식 | **golden 스냅샷 (A), 필요 시 덤프 (C)** | 현행 유지 + 덤프(B) — 아티팩트가 무겁고, 재현해도 시나리오 탓인지 누적 쓰레기 탓인지 못 가린다 |
| 자율 범위 | **①② 자율, ③ 정지 (나)** | ①만(가) — 실제 회귀를 늘 사람이 처리해야 해 자동화가 절반. 판정만(다) — 자동화 이득 최저 |

## 6. 알려진 한계

- 커버리지 숫자(초기 25% 안팎 예상)는 **정보로만** 둔다. CI 하한선은 두지 않는다 —
  숫자를 채우려는 압력이 얕은 테스트를 만든다. 하한선은 숫자가 안정된 뒤 재논의.
- 파서는 굵은 글씨 라벨 네 개에 의존한다. 라벨을 바꾼 문서는 파싱에서 빠지고
  커버리지 표에 「형식 불일치」로 뜬다 (조용히 누락되지는 않는다).
- 흐름 단계 ↔ 액션은 1:1 을 권하지만 강제하지 않는다. 한 액션이 여러 단계를 덮으면
  좌표를 범위(`#5.2-3`)로 적는다.
- `실물재현_E2E_시나리오.md` 는 절차 문서라 좌표 체계 밖이다.
- `E2E_FAST=1` 로 서버를 재사용하면 결정론이 깨진다. 실패 시 리포터가
  「FAST 모드였음 — 재현 전 정상 모드로 다시 확인할 것」을 진단서에 박는다.
