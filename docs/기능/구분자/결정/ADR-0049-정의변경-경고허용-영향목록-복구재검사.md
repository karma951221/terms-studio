# ADR-0049 — 깨지는 사용처가 있는 정의 변경: 구분자 정의끼리는 즉시 차단, 문면 · 상품 사용처는 경고 허용 + 영향 목록 · 복구 경로 · 재검사

## 맥락

기획_UI_전반검토_2026-09-14(아카이브) **F04**. 같은 변경을 두고 문서가 셋으로 갈려 있었다 —

- [[기능/구분자/구분자]] 변경 · 삭제 규칙과 구분자_화면기획(아카이브) §0.3 은 「사용처가 깨지는 식 · 타입 · 레벨 변경도 **경고**로 저장, 확인창 없음」([[기능/구분자/구분자]] §3.3).
- [[기능/구분자/구분자]] 「구분자 식 변경」 · 「부착 레벨 변경」 · 〔D-P1-16〕 은 같은 변경에 「사용처 목록 제시 + **관리자 확인**」.
- 그리고 셋 다 「저장했다 → 무엇이 깨졌는지 알았다 → 고쳤다 → 다시 확인했다」의 **끝**이 없었다. 경고 배지와 관계정보 그래프만으로는 해결 순서 · 담당 화면 · 검사 완료를 알 수 없고,
  깨진 참조를 해소 · 재연결하는 액션은 P1~P6 어디에도 없었다 (구분자_액션 Q3 · README 명세 누락 후보 1 — 모드 폐지로 「전환 차단」이라는 강제 정리 시점까지 사라져 더 벌어진 자리).

같은 날 오전 코드에 사실 하나가 먼저 들어갔다 — 커밋 `c552ee6` (`src/domain/catalog/definitions.ts` `checkDependents`): `D0002 = D0001 and waiver.applies` 인데 `D0001` 을 `no_surrender.type = 'V01'` 로 바꾸면
결과 타입은 boolean 그대로라 통과했고, 그 뒤 `D0002` 가 두 세목 폼을 읽는 규칙 위반이 됐다. 이제 `setExpression` 은 바뀐 정의를 끼운 카탈로그로 **이 구분자를 (전이적으로) 참조하는 구분자들을 다시 검사해 하나라도 깨지면 저장을 거부**한다.
즉 「깨질 사용처는 경고」라는 한 줄이 실물에서는 이미 둘로 갈라져 있었다 — 사용처가 **구분자**면 오류, **문면 · 상품**이면 경고.

[[기능/조립산출/조립산출]] 의 원천 표는 「깨진 참조 → 그 참조가 있는 문면 편집기」 한 줄이었다. 구분자가 구분자를 참조하는 지금은 원인이 **구분자 식**일 수 있고, 세목 범위(`planFormScope` invalid) · 상품 구성(기본계약 · 적용범위)일 수도 있다.
결과 자리에서 문면 편집기로만 보내면 실제 원인을 못 고친다.

## 결정

### 1. 두 층 — 구분자 정의끼리는 즉시 차단, 문면 · 상품 사용처는 경고 + 복구

- **구분자 → 구분자.** 식 · 결과 타입 · 부착 레벨을 바꿔서 **이 구분자를 참조하는 다른 구분자가 규칙 위반**(레벨 규칙 · 세목 폼 · 타입 · 순환)이 되면 **오류 — 저장 거부**. 문구에 어느 구분자가 왜 깨지는지 싣는다 (실물 `checkDependents`, 전이적).
  고치는 길은 둘 — 참조하는 구분자를 먼저 고치거나, 이 변경을 접는다.
- **구분자 → 문면 · 상품.** 같은 변경으로 **문면(조건식 · 반복 · 슬롯 · 공용조항 요구 구분자)이나 상품(세목 범위 · 탑재분 평가)** 이 깨지면 **경고 — 저장되고 배지로 남는다**. 확인창 없음 ([[기능/구분자/구분자]] §3.3 그대로).
  「관리자 확인」은 이 층에 없다 — 편집자가 저장한다.
- 나누는 이유는 §이유. 파괴적 액션(삭제)은 이 두 층과 별개로 ADR-0019 그대로 — **관리자 · 영향 목록 확인 후 허용 · 편집자 요청은 서버 거부**.

### 2. 변경 종류별 표 — 편집 가능 역할 · 즉시 차단 · 저장 후 경고 · 복구 화면

### 3. 경고 상세 — 구분자 → 문면 → 상품 연결과 복구 경로

경고 배지를 열면 한 화면에 셋이 있다.

1. **연결.** 원인(이 구분자 · 무엇을 바꿨나) → 깨진 문면(문서 › 조 › 노드, 왜 깨지나) → 그 문면이 들어가는 상품(탑재분 · 기본계약). 「직접 참조 n건」과 「영향 받는 상품 m건」을 따로 센다.
2. **복구 경로.** 각 줄에 「고치러 가기」(§2 표의 복구 화면) 하나. 원인을 고치는 길이 둘이면(값을 넣거나 문면에서 참조를 빼거나) **실제 원인을 고치는 쪽**이 기본 목적지다 (§4).
3. **재검사.** 원인을 고친 뒤 **「해당 상품 재검사」** 한 번으로 이 경고에 매달린 상품 전부를 다시 평가하고, 해소된 줄은 지운다. 남은 줄만 경고로 남는다. 재검사는 조립(매번 재계산)이라 별도 저장물이 없다.

**같은 원인의 여러 실패는 원인 하나 아래 결과 위치를 묶는다.** 구분자 하나를 잘못 고쳐 문면 세 곳 · 상품 열 곳이 깨지면 경고는 하나이고 그 아래 13개 결과 자리다. 결과 자리마다 경고를 하나씩 내지 않는다.

「깨진 참조를 해소 · 재연결하는 액션」(Q3)은 **새 액션이 아니다** — 원인 화면의 기존 편집 액션(식 변경 · 값 저장 · 참조 제거 · 옵션 선택)이 그것이고, 이 ADR 이 더하는 것은 **거기까지 가는 길(고치러 가기)과 끝났다는 확인(재검사)** 이다.

### 4. 오류 좌표의 원천 표 확장 — 실제 원인을 고치는 기본 목적지

[[기능/조립산출/조립산출]] 원천 표에 세 원천을 더한다.

| 오류 종류 | 원천 (기본 목적지) |
|---|---|
| 구분자 식이 깨짐 (참조하는 구분자 · 필드 · enum 값이 없거나 규칙 위반) | **구분자 편집기, 그 구분자** — 문면 편집기가 아니다 |
| 세목 범위 없음 (`planFormScope` invalid — 세목 폼 둘 · 순환 · 깨진 식) | **구분자 편집기, 그 구분자** |
| 상품 구성 (기본계약 미지정 · 적용범위 빈 특약 · 유효 조합 없음) | **상품모델링, 그 섹션** |

원칙: **원천은 「깨진 곳」이 아니라 「고치면 사라지는 곳」이다.** 문면의 슬롯이 구분자 식 오류로 깨졌으면 원천은 구분자다. 오류 좌표 규칙([[기능/조립산출/조립산출]] §3.4)의 「원천이 여럿이면 첫 번째만」은 그대로 — 첫 번째를 **실제 원인** 쪽으로 정한다.

## 이유

- **구분자 그래프는 정의 시점에 전부 안다.** 구분자끼리의 참조는 위상 순으로 평가되고 카탈로그 하나로 닫혀 있다 — 깨질지 지금 확실히 알 수 있고, 깨진 채 저장하면 다음 사람이 `D0002` 저장 화면에서야 「왜 안 되지」를 만난다. 확실히 아는 것을 경고로 흘릴 이유가 없다.
- **문면 · 상품은 조립이 본다.** 문면이 실제로 깨지는지는 탑재분 값 · 세목 구성 · 기본계약에 달려 있어 정의 시점에는 「깨질 수 있다」까지만 안다. 그걸 오류로 막으면 남의 문면을 먼저 고치기 전엔 구분자를 못 고친다 — 「MVP 는 막지 않는다」([[기능/구분자/구분자]] §3.2 별칭) 그대로. 대신 끝(복구 · 재검사)을 붙인다.
- **관리자 확인은 답이 아니다.** 확인창은 「봤다」만 남기고 「고쳤다」를 만들지 않는다. F04 의 판단 — 「모든 경고를 관리자 승인으로 되돌리는 것도 최신 의도와 맞지 않는다」.
- **원인 하나 아래 결과 묶기.** 같은 원인으로 나온 오류 13개를 따로 보여주면 사람은 13번 같은 곳으로 간다. 리뷰 §8 「결과에서 원인 찾기」 시나리오의 통과 문구가 이것이다.
- **원천은 실제 원인.** [[기능/조립산출/조립산출]] §3.4 의 옛 표 「깨진 참조 → 문면 편집기」는 구분자가 필드만 보던 때의 표다. 구분자가 구분자를 보는 지금 그 표를 따르면 문면 작성자가 남의 구분자 식 오류를 문면에서 고치려 든다.

## 버린 대안

- **사용처를 무효화하는 변경은 전부 차단** (F04 의 대안) — 규칙은 단순하지만 구분자 하나를 고치려면 문면 · 상품을 먼저 다 고쳐야 한다. 실물 이관 중엔 정의가 계속 바뀐다. 기각.
- **전부 경고 (구분자 → 구분자도)** — 2026-09-13 의 「깨질 사용처는 전부 경고」 문면 그대로. 정의 시점에 확실히 아는 위반을 흘려 보내고, 깨진 구분자는 자기 저장 화면에서만 드러난다. 오늘 코드가 이미 이 길을 버렸다 (`c552ee6`). 기각.
- **관리자 확인으로 제한** (구분자_액션 67 · 68행 · D-P1-16) — 「봤다」를 남길 뿐 복구가 없고, 편집자가 자기 식을 못 고친다. 기각.
- **해소 · 재연결 전용 액션 신설** (「깨진 참조 일괄 재연결」 화면) — 대상이 문면 노드 · 값 · 옵션 · 구분자 식으로 제각각이라 화면 하나로 안 되고, 기존 편집 액션과 중복된다. 길과 확인만 더한다.
- **원천 여럿을 전부 나열하는 UI** — [[기능/조립산출/조립산출]] §3.4 「첫 번째만」 유지. 필수 아님 (F04).

## 결과와 감수하는 비용

- 구분자_액션 「구분자 식 변경」 · 「부착 레벨 변경」 · 〔D-P1-16〕 의 「관리자 확인」 → 「경고 + 영향 목록」. Q3 · README 명세 누락 후보 1 · 「아직 열린 것 E」 는 이 ADR 로 닫힌다.
- 구분자_화면기획 §0.3 검사 표에 「참조하는 구분자가 깨짐」이 **오류** 줄로 올라가고, 경고 상세 화면(연결 · 고치러 가기 · 해당 상품 재검사)이 는다 — 구현 P1.
- 오류 좌표 `Coordinate` 의 원천 종류에 구분자 · 세목 범위 · 상품 구성이 는다 — [[공통/기술/아키텍처]] 갱신.
- **경고는 쌓인다.** 「경고 있음」 필터([[기능/구분자/구분자]] §4.1)로 본다. 경고가 사실은 안 깨지는 경우(값이 그 분기를 안 탐)도 재검사 전까지 배지가 남는다 — 재검사가 지우는 것이 규칙이라 감수한다.
- 재검사는 상품 단위 조립이라 상품이 많으면 느리다. 다중산출([[기능/조립산출/조립산출]]) 이전에는 경고에 매달린 상품만 돈다.
- **삭제와의 비대칭** — 식 수정은 참조하는 구분자가 깨지면 거부인데, 삭제는 (관리자 확인 뒤) 참조하는 구분자를 깨진 채 남긴다. 아래 열어 둔 것 ①.

## 열어 둔 것

- [ ] ① **참조하는 구분자가 남아 있는 구분자 삭제** — §1 의 결을 따르면 「참조하는 구분자가 있으면 삭제 거부(먼저 참조를 빼라)」가 맞다. 오늘 코드는 영향 목록에 넣고 관리자 확인 후 삭제한다. 추천안 밖이라 여기 둔다 — 다음 구분자 삭제 구현 때 거부로 올릴지 정한다.
- [ ] ② 「해당 상품 재검사」 버튼의 자리 — 경고 상세 안인지, 상품 미리보기 머리인지 (화면기획에서). 둘 다여도 된다.
- [ ] ③ 세목 범위가 바뀌는 식 수정(세목 폼 A → B)을 경고로 둘지 오류로 올릴지 — 문면은 안 깨지지만 조립 결과가 조용히 바뀐다. 실물 사례가 나오면 본다.
