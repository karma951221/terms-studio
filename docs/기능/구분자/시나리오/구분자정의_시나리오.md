# 구분자 정의 시나리오

> 상태: 초안 · 최종수정: 2026-09-01
> 관련 기획: [[기능/구분자/구분자]] · [[공통/기술/결정/ADR-0005-코드-표시명-이중체계]]

## 시나리오 1 — 구분자 채번: 코드 불변 + 표시명 가변
**전제**: 담보 레벨 구분자 「갱신여부」 미존재.
**흐름**:
1. 정의 화면에서 새 구분자 채번 — 표시명 「갱신여부」, 타입 boolean, 부착 레벨 담보, 노출여부 「무조건 노출」 체크. 코드(예: `renewal`)는 시스템이 자동 부여 — 유저 입력란이 없다.
2. 저장 → 채번 완료. 조건식 편집기는 표시명 칩으로 보여주고, 저장은 코드 기반.
3. 표시명을 「갱신형 여부」로 변경 → 즉시 반영. 이 구분자를 참조하는 식·문면은 깨지지 않는다.
**기대 결과**: 코드는 채번 후 불변, 표시명은 언제든 자유 변경. 저장된 식·경로는 코드 정본.
**경계·오류**: 채번 후 코드 변경 시도 → 거부. **코드는 시스템 자동 채번 — 유저 입력 불가** (2026-09-01 확정). 중복 코드라는 사태 자체가 원천 차단되므로 중복 예외 처리가 없다. 구분자·구조체 필드·enum 값 코드 모두 동일.

## 시나리오 2 — enum 정의와 값 추가
**전제**: enum 「고지유형」 미존재.
**흐름**:
1. enum 「고지유형」 정의 — 값 3개 등록, 각 값 = 코드(불변) + 표시명(가변): 일반심사 · 간편심사 · 건강고지.
2. 상품 레벨 enum 구분자 「고지유형」 채번, 이 enum 참조.
3. 이후 새 값 추가 → 자유. 코드 배포 없이 유효값이 즉시 늘어난다 ([[00_시작/문제정의]] S1).
4. 값 표시명 변경(예: 「간편심사」 → 「간편고지심사」) → 자유. 저장된 값·식은 코드라 깨지지 않는다.
**기대 결과**: enum 값 추가·표시명 변경에 개발 요청이 필요 없다.
**경계·오류**: 값 삭제 — 프로덕션에서 그 값을 고른 저장 값이 있으면 서버 거부. 개발 모드에서는 값 행 연쇄 삭제와 함께 허용 ([[공통/화면/시나리오/역할권한_시나리오]]).

## 시나리오 3 — 구조체(폼) 정의와 필드
**전제**: 급부 레벨 구조체 구분자 「보험금지급」 미존재.
**흐름**:
1. 구조체 구분자 채번 — 코드 `cov_pay`, 표시명 「보험금지급」, 부착 레벨 급부.
2. 필드 추가 — 면책여부 `exempt`(boolean) · 지급률 `pay_rate`(number). 필드도 코드+표시명 이중 체계.
3. 저장 → 폼 하나 = 구조체 하나 = 채번 1회. 식·파생은 경로 `보험금지급.면책여부`(저장은 `cov_pay.exempt`)로 참조.
**기대 결과**: 필드 여러 개를 flat 구분자 여러 개로 채번하지 않는다 — 채번(동일성 판단) 횟수가 준다.
**경계·오류**: 필드 타입으로 구조체 지정 시도 → 거부 (중첩 금지 — 소그룹이 필요하면 폼을 쪼개 별도 채번). **필드 추가는 비파괴** (2026-09-01 확정) — 프로덕션에서도 허용, 기존 저장분(마스터 값·스냅샷)에 새 자리가 미입력으로 나타난다 (트리 노드 추가와 같은 결). 필드 삭제는 시나리오 6 규칙.

## 시나리오 4 — const 구분자: 평균공시이율
**전제**: 문면 템플릿이 평균공시이율을 인용해야 함. 값은 템플릿 작성 시점에 이미 알려져 있다 (2.5%).
**흐름**:
1. const 구분자 채번 — 타입 string, 값 `2.5%`. 값이 마스터 정의에 산다 — 상품이 입력하지 않는다.
2. 문면 템플릿이 이 구분자를 참조.
3. 이율이 2.65% 로 바뀌면 마스터 정의 한 곳에서만 값 변경 → 이후 조립(매번 재계산)에 반영.
**기대 결과**: 전 상품 공통 값의 출처가 한 곳 ([[00_시작/문제정의]] S3).
**경계·오류**: MVP const 는 string 만 — number 등 다른 타입의 const 정의 시도 → 거부. 상품 모델링 화면에 이 구분자의 입력 폼은 나타나지 않는다 (입력 경로 없음).

## 시나리오 5 — 파생 구분자: 면책여부 집계
**전제**: 시나리오 3의 「보험금지급」(급부 레벨, `면책여부` 필드) 존재. 담보 「일반상해사망」 트리에 세부보장·급부 존재.
**흐름**:
1. 담보 레벨 파생 구분자 정의 — 식 `면책여부 = any(보험금지급.면책여부)`. 식은 데이터로 저장 — 코드에 심지 않는다.
2. 집계 범위 = 부착 실체의 하위 트리. 담보에 부착 → 그 담보 아래 전체 급부. 같은 파생을 세부보장에 부착하면 (예: 수술비의 1종수술) 자기 급부들만 집계.
3. 약관 문면의 if 조건식이 이 파생을 참조.
4. 기획자가 정의 화면에서 식을 다시 열람·수정 → 블랙박스 없음.
**기대 결과**: 사내 시스템에서 개발 요청으로 심던 대표 로직이 데이터 정의로 끝난다 ([[00_시작/문제정의]] S1·S4).
**경계·오류**: 다단 파생(파생이 파생을 참조) → MVP 제외, 거부. 집계 대상 급부에 미입력 존재 시 평가 → 조용한 false 없이 오류 + 좌표 보고.

## 시나리오 6 — 사용처 추적(역인덱스) · 삭제 가드 · 타입 변경
**전제**: 구분자 「갱신여부」를 수술비 담보의 문면 조건식과 여러 상품담보의 저장 값이 사용 중. 프로덕션 모드.
**흐름**:
1. 관계정보 뷰(역인덱스)에서 「갱신여부」 조회 → 참조하는 식·문면·저장 값 목록이 나온다 ([[00_시작/문제정의]] S3 역방향 조회).
2. 삭제 시도 → 서버 거부 + 사용처 목록 제시.
3. 개발 모드로 전환 후 삭제 시도 → 참조 목록을 보여주고 확인 후 삭제. 상품담보 값 행 연쇄 삭제, 남은 식·문면 참조는 오류 상태로 표시된다.
**기대 결과**: 사용 중 정의가 조용히 사라지는 경로가 없다.
**경계·오류**: 타입 변경(boolean → enum)·필드 삭제 시도 → 프로덕션 서버 거부. **개발 모드에서는 기존 데이터가 깨진다는 것(소실될 값·깨질 참조 목록)을 보여주고 확인 후 허용** (2026-09-01 — 전면 금지에서 완화). 깨진 참조는 오류 상태로 표시.
