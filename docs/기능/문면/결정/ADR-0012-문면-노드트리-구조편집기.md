# ADR-0012 — 문면 저장: 깊이 비고정 노드 트리 + 구조 편집기

> 상태: 채택 · 날짜: 2026-08-31

## 맥락

문면 저장소의 저장 단위가 [[00_시작/도메인모델]] §7 의 미결이었다. 저장 모델이 정해져야
편집기·사전평가·조립(P6)이 선다. 실물([[00_시작/범위]] 알파Plus)에서 확인된 제약 —

- 조 > 항 > 호 > 목 깊이가 전부 실사용된다.
- **조 하위에 다시 그룹별 조·항·호·목이 오는 구조**가 실물에 존재한다.
  그룹 노드는 MVP 이후 개발하지만, 저장 모델이 이를 원천 배제하면 안 된다.
- 조 번호는 조건 분기로 밀린다 (갱신형 수술비 — 조 하나 추가로 이후 번호 전부 밀림).
- 동적 처리 3종(치환·조건·반복)이 블록 자리와 문장 중간(인라인) 양쪽에 선다.
- 같은 데이터에서 별지 등 다른 문서 종류가 나와야 한다 ([[00_시작/범위]]).

## 결정

1. **문서 = 일반 노드 트리.** 깊이·노드 종류를 스키마에 고정하지 않고,
   **노드 종류별 허용 자식을 규칙**으로 건다. MVP 규칙은 문서 > 조 > 항 > 호 > 목.
   그룹 노드·표 노드의 추가는 규칙의 확장이지 저장 구조 변경이 아니다.
2. 노드는 세 부류 — **구조 노드** · **블록 자리 동적 노드**(조건 블록 · 반복 블록 ·
   공용조항 block 참조) · **인라인 노드**(텍스트런 · 슬롯 · 인라인 조건 · 인라인 반복 ·
   조/별표 참조 슬롯 · 공용조항 inline 참조).
3. **번호는 저장하지 않는다 — 계산값이다.** 조건 해소 후 남은 노드에 순서대로 매긴다.
4. **편집기는 이 트리를 직접 다루는 구조 편집기다.** 블록 추가·이동으로 뼈대를 잡고
   문장은 블록 안에서 편집, 슬롯·인라인 조건은 문장 안에 칩으로 삽입한다.
5. 조의 메타는 조 명 · 조연결 뿐이다.

## 이유

- 그룹 구조가 실물에 있고 MVP 이후 개발이 확정이다 — 4단 고정 스키마면 그때 못 끼운다.
- 사전평가 톤다운·공용조항 부착 검사·참조 슬롯 삽입은 **트리 위에서만 자연스럽다.**
- 조립의 입력·출력이 모두 순수 데이터가 되어 산출물 스냅샷 회귀 비교의 기반이 된다.
- 노드 종류가 열려 있어 별지 등 다른 문서 종류도 같은 저장 모델을 쓸 수 있다.

## 버린 대안

- **A. 조>항>호>목 4단 고정 스키마** — 단순하고 쿼리·화면이 곧다. 기각: 그룹 구조를
  못 끼우고, 표·별지 등 노드 종류 확장마다 스키마 공사가 된다.
- **B. 자유 텍스트 + 마크업 저장** (`{{슬롯}}` · `#if` 를 품은 텍스트) — 타이핑이 빠르다.
  기각: 텍스트 ↔ 트리 변환이 상시 필요하고, 톤다운·부착 검사 UI 가 성립하지 않으며,
  참조가 텍스트 안에 박혀 참조 무결성(그래프 검증)을 걸 수 없다. 유저 판단: 쓰기도 불편하다.

## 결과와 감수하는 비용

- 허용 자식 규칙이라는 관리 지점이 한 겹 생긴다 — 규칙 위반은 저장 시점에 거부한다.
- 렌더러·편집기가 임의 깊이를 감당해야 한다 (재귀 렌더).
- 구조 편집기는 자유 텍스트보다 초기 구현량이 크다 — 원문 이관도 수동이라 이관 비용을
  편집기 UX 가 감당해야 한다 (단, 이관은 공용조항 추출·조건 설계를 동반하는 기획 판단
  작업이라 자동 분해의 실익이 작다는 판단 — 2026-08-31).
