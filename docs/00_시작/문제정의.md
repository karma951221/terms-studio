# 문제정의

> 상태: 초안 · 최종수정: 2026-09-14

## 무엇이 문제인가

**구분자와 모델링이 일치하지 않아, 유효값을 사람이 코드로 떠받치고 있다.**

기준점은 사내 약관시스템이다. 거기서 벌어지는 일 —

1. 구분자가 모델링과 따로 논다. 구분자의 **유효값을 모델에서 끌어낼 수 없다**.
2. 그래서 유효값·파생 로직을 **구분자마다 개발자에게 요청해 손으로 구현**한다.
   예: `보험금지급.면책여부 = any(급부1면책여부, 급부2면책여부, …)` 를 개발 요청 → 약관 조건식이 이를 읽는다.
3. 구현된 로직은 **블랙박스**다 — 기획자는 식을 다시 볼 수 없고, 로직이 구분자 수만큼 쌓인다 → **버그**.
4. 구분자가 많아질수록 이미 있는 것을 찾지 못한다 → **중복 채번**.
5. 중복 채번이 구분자를 더 늘린다 → 1 로 돌아간다.

핵심은 개별 증상이 아니라 **이 고리가 스스로 돌아간다**는 것이다.
구분자를 하나 고치는 일이 다음 구분자를 낳는다. terms-lab 도 같은 고리에 진입했다고 판단해 폐기했다.

## 중복 채번을 파고들면 — 이 프로젝트의 진짜 어려움

중복 채번의 원인은 두 갈래이고, **두 번째가 본체**다.

**(a) 못 찾아서.** 같은 개념인데 이름만 다른 구분자가 이미 있는 줄 몰랐다. → 탐색·검색의 문제.

**(b) 같은 개념인지 판단할 근거가 휴리스틱이다.** ← 이쪽이 어렵다.

### 기준 사례 — 체증·체감납

| 구분자 | 타입 | 성격 |
|---|---|---|
| `체증·체감납 여부` | boolean | 상품 구조에서 **직접** 결정된다 |
| `보험료 가벼운 납입형 여부` | boolean | 현재 운영상 위와 **값이 항상 같다** |

두 구분자는 **개념적으로 명확히 다르다.** 그런데 지금 체증·체감납을
「보험료 가벼운 납입형」이라는 종형으로만 운영하고 있어서, **현재는 같은 의미로 쓰인다.**
새로운 상품구조가 나오면 갈라진다.

> **처음부터 `체증·체감납 여부` 하나만 땄어야 했다.**
> 「보험료 가벼운 납입형」은 그것에서 유도되는 이름이지, 별도로 결정되는 값이 아니다.

여기서 나오는 규칙 후보 —

- 구분자는 **「지금 값이 같은가」가 아니라 「무엇을 근거로 결정되는가」로 나눈다.**
  우연히 값이 일치하는 두 개념을 합치면 나중에 갈라질 때 못 나누고,
  근거가 같은 것을 둘로 나누면 그게 곧 중복이다.
- 값이 다른 값에서 유도되면 그것은 구분자가 아니라 **파생**이다.
  상품구조가 바뀌면 파생의 식만 고치면 된다. → [[README]] ADR 후보

### 그리고 되돌릴 수 없다

중복을 뒤늦게 발견해도 **지울 수 없다.** 각 구분자로 이미 모델링한 건들이 존재하기 때문이다.
그래서 이 문제는 **탐지가 아니라 예방**의 문제다. 채번하는 순간에 막아야 한다.

## 구분자 수는 실제로 줄어드는가

**줄어든다고 본다.** 폼 하나에 여러 필드를 입력할 때, 기존에는 flat 한 구분자를 여러 개
채번했지만 모델링과 일치시키면 **구조체 하나만 채번**하면 된다.

> ⚠ 단, 줄어드는 것은 **필드 수가 아니라 채번 횟수**다. 구조체 안의 필드는 그대로 남는다.
> 그래도 이득이 실재하는 이유 — **채번은 사람이 「이게 기존 것과 같은가」를 판단하는 행위**이고,
> 중복은 그 판단이 실패할 때 생긴다. 판단 횟수가 줄면 실패도 준다.
>
> 이 이득이 성립하려면 **묶는 단위가 의미 있는 단위**여야 한다 —
> 폼 하나가 개념 하나여야 한다. 아무렇게나 묶으면 이름만 길어진 네임스페이싱이다.
> → 「폼 하나 = 구조체 하나」의 분할 기준이 필요하다.

## 누구의 문제인가

**지금은 만드는 쪽의 문제다.** 유효값 로직을 짜는 사람, 구분자를 채번하는 사람이 아프다.
terms-studio 를 쓰는 사람은 아직 없다.

> 다만 목적은 쓰는 쪽에 있다 — **유저가 약관 생성 결과를 이해하고 따라갈 수 있을 것.**
> 지금 검증할 수 있는 것은 만드는 쪽 지표이고, 진짜 목표는 아직 검증할 수 없다.
> 이 간극을 인정하고 시작한다. → Q1

## 왜 다시 시작하나

terms-lab 은 어느 정도 개발이 진행된 시점에 방향이 틀렸다고 판단해 폐기했다.
값의 출처가 하나 늘 때마다 그 값을 읽는 경로가 하나씩 새로 뚫리는 구조였다 — 고칠수록 갈래가 늘어난다.

> 당시 진단은 [[_archive/01_기획/구분자_단일출처_기획]] §2·§3.
> **참고만 한다.** 전제는 여기서 다시 세운다.

## 성공은 어떤 모습인가

- **S1. 구분자를 추가할 때 코드를 한 줄도 건드리지 않는다.** 유효값이 데이터에서 나온다.
  → **MVP 범위 (2026-09-12, [[기능/마스터/결정/ADR-0037-입력항목-코드마스터-유저정의폼-MVP이후]])**: 구분자(식)와 열거형변수 값에만 성립한다. 입력 항목(레벨별 마스터 필드)은 코드라 추가가 배포다 — 유저 정의 폼은 MVP 이후.
- **S2. 구분자를 만드는 순간, 결정 근거를 설명하고 기존 개념을 재사용할 수 있다.**
  → **2026-09-14 개정 ([[기능/구분자/구분자]] §3.6)**: 시스템은 개념 중복을 「막는다」고 보증하지 않는다 — 같은 결과의 두 식이 다른 개념일 수 있고, 같은 개념이 다른 식으로 쓰일 수 있으며, 별칭은 허용 + 경고다([[기능/구분자/구분자]] §3.2).
  보증하는 것은 **채번하는 순간 판단할 근거가 그 자리에 있다**는 것 — 기존 구분자 검색 · 정의 설명(무엇을 근거로 결정되는가) · 「이 구분자를 쓰기」로 직접 참조로 돌아가는 길. 판단은 사람의 도메인 판단이다 (Q2 의 답 — 후보 제시).
- **S3. 값 하나를 짚으면 어디서 결정됐는지 답이 하나로 나온다.**
- **S4. 체증·체감납 사례를 통과한다.** 이 시스템에서 「보험료 가벼운 납입형 여부」를 만들려 할 때 생성 화면이 「체증·체감납여부」를 찾아 보여주고,
  작성자가 **새 채번 없이 기존 개념의 직접 참조**로 끝낼 수 있다. 별칭으로 만들어 버려도 경고 배지 + 「직접 참조로 바꾸기」 경로가 남는다. ← **인수 시나리오 1호**
  (2026-09-14 개정 — 통과 조건은 「재사용 경로가 존재하고 그 길로 끝낼 수 있다」, 차단 검증이 아니다 → [[기능/상품/시나리오/체증체감납_인수시나리오]] 개정 대기)
- **S5.** *(쓰는 쪽 지표 — Q1 이 답해지면 추가)*

## 열어 둔 질문

- **Q1. 쓰는 쪽 목적을 어떻게 검증하나.** 사용자 없이 "이해하고 따라갈 수 있다"를 확인할 방법.
- **Q2. 동일성 판단을 시스템이 어디까지 도울 수 있나.** 「체증·체감납이 더 근본이다」는
  결국 사람의 도메인 판단이다. 시스템이 할 수 있는 건 후보 제시인가, 규칙 강제인가.
  → 2026-09-01 일부 결정: MVP 는 구조 장치(별칭 파생 금지·코드 자동 채번·폼=구조체)로
  막고, **유사 후보 제시는 MVP 이후 기획** ([[00_시작/범위]]).
  → 2026-09-14: 답은 **후보 제시**다 ([[기능/구분자/구분자]] §3.6). 별칭 금지는 경고가 됐고([[기능/구분자/구분자]] §3.2), 남은 구조 장치는 코드 자동 채번 · 표시명 중복 거부 · 복제 없음. 이름 · 설명 · 식 본문 검색과 정보 등급 「같은 식 후보」로 시작하고, 의미 유사 검색은 여전히 MVP 이후.
- **Q3. 「폼 하나 = 구조체 하나」의 분할 기준.** 무엇을 한 폼으로 묶는가.
- **Q4. 「모델링 = 구분자 타입 일치」는 전제인가 결정인가.** 결정이면 대안과 비교해 ADR 로 남긴다.
